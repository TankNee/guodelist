# 同步机制与测试

## 数据模型

桌面端把任务、清单和删除墓碑（tombstone）一起持久化在 `localStorage`：

```text
tasks[]   id, listId, updatedAt, done, dueDate, ...
lists[]   id, name, emoji, groupId, updatedAt
removed   { tasks: { [id]: deletedAt }, lists: { [id]: deletedAt } }
```

每次同步发送完整本地快照和墓碑；服务端按账号合并后返回完整快照。客户端再用同一套纯函数
`mergeRemote` 做一次合并，避免多设备互相覆盖。

## 合并规则

`src/lib/syncMerge.ts` 是唯一实现，桌面 store 和测试共用：

1. **LWW**：未被删除的记录按 `updatedAt` 合并，较新的获胜；相同时间以远端为准。
2. **墓碑优先**：对已知 id，删除是永久的，不因另一台设备发来较新的旧副本而复活。
3. **墓碑只影响本账号已知的 id**：旧版本服务端曾返回全局墓碑，必须忽略陌生 id。
4. **清单删除级联任务**：清单墓碑生效时，清单和它的任务一起删除。
5. **inbox 永不删除**：虚拟收件箱不参与清单删除。
6. **未知/缺失时间戳**：没有 `updatedAt` 的旧记录按服务端当前时间补戳，避免旧客户端改名被丢弃。

> 0.9.5 进一步收紧了删除语义：0.9.3 修复了“旧墓碑误删新清单”，但旧客户端仍可用更新的
> `updatedAt` 把已删除清单重新推回来。现在服务端和桌面端都把墓碑视为最终状态；删除后必须显式
> 创建新记录（新 id）才会出现。
>
> 0.9.4 的 v6 迁移会清空一次旧墓碑，因此升级前已被迁移清掉删除记录的清单可能已经回到服务器；
> 这类历史清单需要在 0.9.5 里再删除一次，之后不会被复活。

## Today 视图

`Today` 严格等于 `task.dueDate === dayKey`：

- 11 月 6 日的 Today 只显示 11 月 6 日到期的任务；
- 11 月 2 日/4 日的逾期任务留在「全部任务」，不会混进 Today；
- 侧边栏 Today 计数使用同一个严格条件；
- 逾期任务仍然可以在「全部任务」中查看和处理。

## 同步调度

- 本地修改后 2.5 秒防抖推送；
- 每 60 秒、窗口 focus、网络恢复时拉取；
- 请求进行中又发生修改时设置 `queued`，当前请求结束后再合并一次，避免慢请求丢更新；
- 合并期间设置 `applying`，避免应用远端结果触发再次推送风暴。

## 手工验证

1. 把一条任务改成 11 月 2 日，Today 不应出现；全部任务中应出现。
2. 在手机新建清单并在桌面点“立即同步”，侧边栏应出现该清单。
3. 在桌面改名清单，等待 2.5 秒后手机同步，名称应更新。
4. 删除清单后，两端清单和其任务都应消失；不要在另一台机器上“复活”。
5. 同步过程中快速连续改两条任务，最终两端都保留最新版本。
